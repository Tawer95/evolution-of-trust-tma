Сгенерировать НЕТЕХНИЧЕСКИЙ отчёт о прогрессе по завершённому этапу (для нетехнического стейкхолдера / поста-апдейта): $ARGUMENTS

Читатель — не разработчик. Объясни **ЧТО** сделано и **ЗАЧЕМ** (какую ценность даёт игроку / проекту), простым языком. Переводи жаргон: «приложение запоминает, где ты остановился» вместо «CloudStorage persistence»; «защита от накрутки очков» вместо «initData HMAC + score binding»; «таблица лидеров» вместо «leaderboard API». Без эмодзи, без хайпа.

## Источник правды (anti-invention)
Бери ТОЛЬКО реально сделанное на этапе — НЕ выдумывай фич:
- свежий PR (title + body), `git log` коммитов этапа;
- `docs/manual-tests/<slug>.md`, `docs/ARCHITECTURE.md` (статус этапа), план этапа.
- Фича отложена → НЕ пиши, что готова. Честно говори, когда этап — «фундамент» без видимых пользователю фич.

## Формат (строго)
Сохранить в `docs/progress-reports/<slug>.md` (папка **gitignored** — личный канал, вне репо):
- Заголовок: `# Эволюция доверия (TMA) — этап «<Название>» завершён` + строка `**Дата:**` (абсолютная).
- **## Коротко** — 2–4 предложения: что за этап, какую ценность даёт; честно, если это инфраструктура без видимых функций.
- **## Что сделано** — нумерованный список: простым языком + (где уместно) зачем важно. Процессы по-человечески.
- **## Качество** — гейты простым языком (N автотестов зелёные, проверено в Telegram на телефоне и десктопе, аудит безопасности пройден). Без названий инструментов-жаргона.
- **## Что дальше** — следующий этап в 1–2 предложениях.

## Процесс
1. Собрать факты этапа (PR, git log, manual-test, ARCHITECTURE) — ничего не выдумывать.
2. Написать `docs/progress-reports/<slug>.md`.
3. Показать полный текст в чате — чтобы юзер скопировал и отправил.

Тон: спокойный, по делу. Техническую гарантию переводить в выгоду (надёжность, защита результатов игроков, скорость дальнейшей разработки).
